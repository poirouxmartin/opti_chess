# opti_chess audit (2026-10-12)

Scope: full read of the engine (board, movegen, FEN, search, eval, GUI, tests, build, CI),
a headless harness, bug reproduction and fixes, then a structure proposal.
Every bug below carries how it was confirmed:

- **RUN**: reproduced by executing a binary (perft, CLI, gtest, CI log).
- **READ**: confirmed by reading the code (deterministic, no run needed or not runnable here).
- **HYP**: hypothesis; plausible from the code, not reproduced.

**Data flow (analysis):** GUI (or PuzzleRunner/CLI) builds a `Board` from FEN -> wraps it in a
root `Node` -> `Node::grogros_zero()` iterates: select a child by UCT-like score
(`pick_random_child`), expand new moves (`explore_new_move`) which runs a bounded
alpha-beta quiescence on the new leaf, back up `_deep_evaluation` (white-relative cp + WDL).
Boards and nodes come from thread_local arenas (`monte_board_buffer`, `monte_node_buffer`);
a thread_local TT and an optional DAG node map share transpositions. The GUI runs the search
on a worker thread and reads a snapshot for display.

**Board representation:** `uint8_t _array[8][8]` (0 empty, 1-6 white P N B R Q K, 7-12 black),
`uint64_t _bitboards[13]`, `_occupancies[3]`, cached king squares. `Move` is a 4-byte bitfield
(from/to row/col, 2-bit promotion piece, flags). Legal movegen is direct (pins + check mask
computed first), all four promotions are generated. `make_move` is in place on a copy
(copy-make); `unmake_move` exists but is dead and wrong (B-10). Move lists live in the Board
(`_moves[100]`, see B-09).

**Eval:** handcrafted, phase-aware, ~40 weighted terms, returns white-relative cp, a WDL
estimate and an uncertainty. No NNUE in this tree.

**Training pipeline:** none in C++. `scripts/*.py` only download Lichess puzzles/evals;
`selfplay.cpp` compares search parameter sets.

## 2. Build setup

- CMake 3.24+, preset `windows-release` (no generator pinned, binaryDir
  `opti_chess/build/windows-release`). The local tree is generated by **Visual Studio 18
  (Insiders)**; the VS 2022 CMake cannot drive it. Use
  `C:\Program Files\Microsoft Visual Studio\18\Insiders\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe`.
- Targets: `opti_chess` (GUI), `engine_lib` (static, everything but main/tests.cpp),
  `opti_chess_tests` (gtest), `opti_chess_selfplay`, `opti_chess_cli` (new).
- MSVC flags: `/Ox /fp:fast /GL /Oi /Ot /Ob3 /GS- /bigobj`, `/LTCG`, 16 MB stack.
- Release exes land in `opti_chess/build/windows-release/Release/`. AGENTS.md said
  `build/release/Release/` (that tree only holds a stale vcxproj); a note now points to the
  real tree.
- `board.cpp` and `board.h` were UTF-16LE (grep, diffs and most tools could not read them);
  converted to UTF-8 by this audit with no content change.

## 3. Headless harness

`opti_chess_cli` (no window, links engine_lib) and `scripts/harness.ps1`:

| command | what |
|---|---|
| `opti_chess_cli perft <d> [fen]` | node count, time, Mnps |
| `opti_chess_cli divide <d> [fen]` | per-move counts (UCI notation) |
| `opti_chess_cli perft-suite [quick\|full]` | startpos, kiwipete, positions 3-6, promotion storm vs reference counts; exit 1 on mismatch |
| `opti_chess_cli bench [iters]` | 8 positions, fixed iteration budget, OPTI_SEED=42; prints nodes/s and a signature (bestmoves + node counts) to detect behaviour changes |
| `opti_chess_cli uci` | minimal UCI: uci, isready, ucinewgame, position startpos/fen + moves, go nodes/movetime/wtime/btime/winc/binc/infinite, quit |

Limitations: `go` is synchronous (`stop` is ignored); `position ... moves` is replayed into a
FEN, so repetition history before the last move is not passed to the search.

`scripts/harness.ps1` builds tests + GUI + CLI from one tree in one command, then runs
perft-suite, the gtest regression set (CI exclusions), a UCI smoke session and bench.

## 7. Structure: proposal and decision

### Problems found

1. **Layering is inverted.** The engine reaches into the GUI global `main_GUI`: 181 references
   in board.cpp, board_fen.cpp, board_display.cpp, eval_core.cpp (76, eval breakdown display),
   eval_king.cpp (53), eval_pawn.cpp (13). `board.h` includes raylib for three display members.
   Consequences: `engine_lib` must compile gui.cpp and link raylib, `from_fen` mutates GUI
   state (B-20), and no target is truly headless.
2. **Huge flat translation units.** board.cpp 3.2k lines (state + movegen + perft + mobility
   helpers + bitboards), exploration_diag.cpp 3.5k, gui.cpp 3k, eval_king.cpp 2.6k, all in
   one flat directory with tools, GUI and tests' legacy harness.
3. **Dead and duplicate code** (B-10, B-12, B-22).
4. **Three build descriptions**: CMake (authoritative, used by CI), `opti_chess/opti_chess.vcxproj`
   (the .sln), and the tracked `build/release/opti_chess.vcxproj` with absolute paths of another
   machine (`C:\Users\mpoiroux\...`) used for the baseline worktree.
5. **Tuning by globals and environment variables** read in search code (`g_*` flags,
   `getenv("SHARED_TRACE")` per iteration, `OPTI_*` knobs in eval), and searches leave state
   behind for the next one (section 5, bench note).

### Target layout (decision)

```
opti_chess/
  core/     board.h board.cpp movegen.cpp fen.cpp zobrist.*       (no GUI, no raylib)
  eval/     evaluation.* eval_*.cpp                               (no GUI)
  search/   exploration.h search.cpp buffer.*                     (no GUI)
  tools/    cli.cpp selfplay.cpp puzzle.* stockfish_adapter.*
  gui/      main.cpp gui.* main_gui.h game_tree.* board_display.cpp tests.cpp windows_tests.*
  tests/
```

CMake: `engine_core` (core + eval + search, no raylib) <- `engine_tools` <- `opti_chess_cli`,
`opti_chess_selfplay`, `opti_chess_tests`; `opti_chess` (GUI) = engine + gui/ + raylib.

Engine -> GUI communication becomes one-way: the eval writes its per-term breakdown into an
optional caller-owned struct (nullptr in search, filled only by the GUI), exactly like the
`EvalControls` diet of TD-004, so the hot path keeps a single predictable branch; `from_fen`
becomes a pure parser and the GUI calls its own `load_position()` wrapper for PGN, orientation
and game tree.

**Trade-offs.** Directories and library split make the headless build real and cut rebuild
times, and each engine module becomes testable without a window. Costs: renames conflict with
long-lived branches (feature/tt-main-search) and invalidate the copied vcxproj of the
`../opti_chess_baseline` worktree (AGENTS.md baseline discipline); the eval decoupling touches
76 + 53 + 13 sites in hot eval code and must pass the eval gates (EvaluationSuite, quiet-bank
MAE) and NPS. Splitting a TU can lose inlining without LTCG: with `/GL` + `/LTCG` it should not,
and every step is measured.
